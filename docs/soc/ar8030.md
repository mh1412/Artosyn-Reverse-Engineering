# Artosyn AR8030 radio and Open8030

[SoC studies](README.md) · [Documentation index](../../README.md)

## Role in the system

AR8030 is a separate radio/baseband processor. It transports payloads and runs
radio control firmware; the application host handles the camera, media decoder,
display or UI as appropriate to the device.

Ascent Gnd485 uses SDIO between its Linux host and radio. Skydroid G11 uses an
internal USB connection. A shared radio family does not make the loading
procedure, board profile or transport wiring interchangeable.

## Firmware reconstruction

Initial offline analysis compared matched 17.5.8 GND and SKY radio payloads.
These contain RISC-V code, distinct from the AArch64 or ARMv7 host executables.
Analysis recovered different board-initialization selectors and identified one
previously unresolved custom operation as T-Head `th.mula`.

Synthetic ELF headers and analysis mappings are tooling metadata. They do not
establish the original firmware's ABI, declared permissions or temporal boot
order. Address-specific findings also require the matching payload hash; a
17.5.8 map must not be applied blindly to 18.21.10.

Early Zephyr work executed on the physical radio and exchanged diagnostics over
SDIO. That stage did not implement a working PHY/MAC or end-to-end video.
The [physical bring-up history](../experiments/ar8030-sdio-and-rf-bringup.md)
documents the host-mask race, queued buffers, calibration and failed reception
despite selected stock clock/GPIO matches. It also separates restored radio
identity from verified stock-video recovery.
The [receive-startup study](ar8030-receive-startup.md) and
[acquisition experiments](../experiments/ar8030-receive-acquisition.md) distinguish
power/interrupt activity, invalid hardware headers and the first checked MAC
control packets, before native peer admission or video existed.
The following [uplink/login experiments](../experiments/ar8030-uplink-and-login.md)
trace TX-profile and gain corrections, AP assignment, synchronization ACKs and
bounded request-ID recovery before host-socket delivery was implemented.
The [boot and worker reconstruction](../firmware/ar8030-boot-and-lifecycle.md)
and [early receiver trials](../experiments/open8030-early-dev.md) trace the later
transition to source-bootstrap, normal-loader and host-lifecycle video operation.
The subsequent [candidate-recovery and power experiments](../experiments/ar8030-recovery-and-power.md)
separate same-peer recovery from physical peer loss, and working factory-offset
fallback from unresolved low-level acquisition behavior.

## Open8030 validation

Later Open8030 v0.2.0 validation covered a standard Ascent VRX in DEV role and
an Ascent Lite board-482 VTX in AP role, both using matched 18.21.10 inputs.
A five-minute bench test delivered 605 MB, with all 293 sampled link states
connected and a visible camera scene captured through an HDMI-to-USB adapter.

The same test recorded 7,988 dropped receiver queue bytes and brief AP write
rejections; transport recovered without intervention. This establishes bounded
radio/video operation, not lossless transport, range/interference performance,
full telemetry/RC parity or a 35+ Mbit/s throughput result.

Stop/start recovery was exercised on both roles. The public loading helper at
that stage supported VRX; the AP image required a board-specific RAM loader.
USB receivers and other variants were outside that release's validation scope.

## Implementation and firmware boundaries

Open8030 replaces the radio processor firmware. It does not by itself replace
the application host's OS, video backend, decoder or UI. The matched source build
also requires board-profile data; the public source alone did not provide all
inputs necessary to reproduce the validated RF image.

Radio roles called AP and DEV are not a claim of IEEE 802.11 interoperability.
Recovered wireless notes describe exposed MAC bytes and PHY control fields,
not a complete I/Q, coding/interleaving or waveform specification.
