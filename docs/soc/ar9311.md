# Artosyn Proxima-9311 / AR9311

[SoC studies](README.md) · [Documentation index](../../README.md)

## Application processor and memory

The standard Ascent Gnd485 receiver's live device tree identifies
`artosyn,proxima-9311`. Its application CPU has two Cortex-A53 cores, observed at
800 MHz. Older `ar9301` names in IP-block strings or boot variables do not
override the root platform identification.

The recorded Gnd485 memory configuration describes 512 MiB:

| Region | Role |
| --- | --- |
| `0x20000000–0x2fffffff` | Linux region, including reservations |
| `0x30000000–0x3fffffff` | Vendor media memory; used as a codec DMA pool in the custom media work |

This is a board-specific configured layout. A reference firmware DT that declares
a larger range does not prove that more physical RAM is fitted.

## Video codec

The integrated codec identifies as Chips&Media **Wave521C**, product `0x521c`.
The host-side Linux `wave5` driver and the codec CPU firmware are separate layers.
The working codec firmware is `chagall.bin`; an open host driver does not make
that firmware open or establish that its instruction set is ARM.

Custom Linux bring-up demonstrated hardware H.264 and H.265 full-frame decoding
through a V4L2 stateful decoder. Matching the host-decoded output and repeating
sessions provide stronger evidence than successful initialization alone.

[Slice experiments](../experiments/ar9311-slice-decoding.md) demonstrated correct
supplied regions after forced picture completion, while resumable slice decoding
and early scan-out remained unproven.

## Display

The Gnd485 display path runs through Artosyn VO, MIPI-DSI and an external HDMI
bridge. The owner reported an LT9511 marking. Software behavior and register
reads supported useful LT9611 compatibility, but do not independently confirm
the package identity.

Later fixed-mode HDMI tests demonstrated cold-boot scan-out, changing two-buffer
page flips and concurrent hardware decoding. One run completed 10,800 flips at
about 60.0088 Hz. That measures display events, not camera-to-display latency or
support for every HDMI mode.

The [display-pipeline study](../systems/ar9311-display-pipeline.md) records
the fixed timing and DMA ownership. The [HDMI investigation](../experiments/ar9311-hdmi.md)
distinguishes working output from the later selector-access fix and unresolved
line artifacts/black intervals.

## GPIO correction

Early inherited documentation treated direction registers as unreadable.
Gnd485 readback instead agreed with configured directions. Vendor driver analysis
also showed direction-register reads during initialization and suspend handling.

The evidence supports direction readback on the investigated AR9311 controller.
It does not test every silicon revision. Preserving inherited output directions
matters: assuming all pins are inputs can release unrelated bootloader outputs
when the first consumer changes a direction.

## Clocks and watchdog

MMC work established independently managed radio and SD source clocks with
board-specific selection/phase settings. On Gnd485 the tested sources ran at
100 MHz, with card clocks limited to 50 MHz. Gate-recovery tests and an SD
unbind/rebind experiment checked restoration and isolation between controllers.
These results do not establish general CPU, DDR, display or USB clock ownership.

The watchdog was observed resetting the board after feeding stopped. Boot
firmware could leave it running even when the initial software state appeared
inactive. Reliable watchdog stop/halt requires reset-controller behavior beyond
an inactive status or `nowayout=0` setting.

## Board boundaries

The [P1 camera study](ar9311-p1-camera.md) adds source capture and hardware
encoding on an SC231AI-equipped board with 256 MiB memory. Its separate DMA
pools, sensor controls and codec microcode differ from the Gnd485 decoder setup.
It includes cold recordings, full camera-module reloads and source AE/AWB tests.

Gnd485 radio reset/power wiring differs from the related goggle platform.
AR9311 register behavior can be shared; GPIO assignments, camera presence,
display connections and power sequencing require device-specific evidence.

The [platform register study](ar9311-platform.md) supplies the GPIO numbering,
Gnd485 pin assignments, MMC gate masks and reset limitations. Its
[validation record](../experiments/ar9311-platform-validation.md) separates
RAM bring-up, fault controls and later installed-platform results.

The [stock GE2D study](ar9311-ge2d.md) adds the bitmap/RPC and MMZ contracts,
hardware alpha/copy results and unresolved DMA-recovery boundaries. Its exact
offscreen copies do not establish an integrated UI compositor or a GLES stack.
